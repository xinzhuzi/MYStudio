# 保序压缩(OPCC)可行性试验与检查器缺陷实证(2026-11-26)

> 调研用原型与试验脚本放仓库外临时目录,**不入仓**;本文记录方法、数据与结论,供执行阶段重写为技能工具时参照。
> 所有数字都是本日实跑所得;逐件原始数据见文末「试验数据」。

## 一、要解决的三个问题在坐标上是什么

| 问题 | 坐标判据 | 现状(149 件 GUI / 201 作用域) |
|---|---|---|
| ① 分组互相遮盖 | 任意两个组框矩形有交集(立宪检查器已有 `group_overlap`) | 13 件 / 36 对 |
| ② 节点超出分组框 | 节点盒与某组框相交却没有完全落在里面 | 93 件 / 470 节点(est 口径);另有 298 个节点虽在内但贴边 |
| ③ 间距过远 | 相邻节点之间净隙过大:同行横隙 >400、同列纵隙 >240、直连两节点横向净距 ≥1200 | 147 件;主力件整图可见需缩到 0.1–0.3 倍 |

「节点盒」有两种口径,必须分清(本役最关键的认识):

- **可视盒**=节点声明的 `size`,画布上实际画出来的大小;
- **est 盒**=立宪检查器的 `est_size` 足迹(标题 36 + 槽行×24 + 控件×30 + 垫 28,预览类再 +260,宽≥250),是**故意偏大**的估算。例:UNETLoader 实际高 84px,est 算成 172px。

所以:组框包不包得住、节点离得近不近,只能按**可视盒**量;est 盒只用来保证「不新增 est 违规」。按 est 盒去「抬」节点,会把作者手排的紧凑列撑开一倍,与需求相反(原型第一版就踩了这个坑)。

## 二、方法:保序压缩(只收不推)

把原布局里「谁在谁左/右/上/下」的关系写成差分约束 `u ≥ v + d`,`d`=两者可视净隙夹到 `[原值与目标取小]`:

1. **解叠**:可视盒真重叠的节点对,沿侵入最浅的轴把连线少的那个挪到最近合法空位(只动真重叠的)。
2. **成员判定**:节点可视盒中心落在组框内 → 属于该组;否则与组框交叠面积 ≥25% 也算;落入收紧盒的无组节点收编。
3. **节点对约束**:某轴分开 → 净隙 `min(原值, 目标)`;某轴交叠 → 该轴相对位置**刚性保持**(保住作者的对齐与错位,不被最小不动点吸平)。
4. **组框约束**:组框=成员可视盒包围盒+立宪留白(左 30/上 50/右 30/下 30);组间按原方位分开(两轴都交叠的组按多数成员对的方位定关系);非成员节点与组之间保留原间距。
5. **线带约束**:原在某条线整体上方/下方的节点,压缩后仍留在外侧。
6. **求解**:强连通缩点 + 最长路径 = 最小不动点(零权和环合法;正环=不可解)。
7. **线遮修补**:解出来若有新「线穿节点」,逐个试「推到线下方/上方」,位移小的优先;不可解或没消掉就回退换向。
8. **档位梯子**:目标档从最紧凑开始逐级放松,取**第一个过守门**的档;都不过则退到「只动组框、不动节点」的保底档。

性质:相对次序全保;过大空隙吸到目标值;原本就小的间距原样保留;恒等档逐坐标恒等。

## 四、试验数据(全量 149 件,2026-11-26;原型为调研件,已知缺陷见 §六)

候选范围 = 剔除官方件 5、原件 2、收据钉死 1,共 **140 件**(另有 1 件混合 id 检查器报错)。

### 4.1 守门策略 × 压缩档位(档位 = 最紧档 1 → 放松 1.5 / 2 → 不压缩 `inf` → 保底「只动组框」)

### 4.3 为什么多数件压不动:体量来自流水线长度,不是空隙

以 `一镜到底-分段.json`(17353×5048)为例:7 个阶段组框横排,相邻组间净隙只有 170–210px,组内节点横向填充率 61–196%(已经叠在一起)。它显得「间隔长」,是因为顶行只有最左的加载器和最右的保存节点,中间隔着整条流水线。保序压缩只吸空隙,不会把长流水线折行,所以宽度不变。要缩短只能**重排**(把长链折成两行),那会改变节点的相对位置。

### 4.5 组框类(R2 / R3)的现状

「只动组框」模式全量:分组互遮 36 → 0,但代价是主图层并组 69 次,且节点出组框 121 → 614——原型把组框按成员重算后留白外扩,把邻近节点卷了进去。**说明组框修复不是「重算包围盒」这么简单**:节点归属、留白外扩与邻组的冲突必须和节点位置一起解。这部分原型没做对,见 §六。

## 六、原型的已知缺陷(正式实现必须解决,不是方法上限)

| # | 缺陷 | 表现 | 正式实现的对策 |
|---|---|---|---|
| a | 组成员判定与留白外扩没和节点位置联立解 | 「只动组框」并组 69 次、出组框 121→614 | 成员归属先定;组框=成员包围盒+留白;被外扩卷入的非成员节点作为约束推开(与压缩同一次求解) |
| b | 两轴都交叠的组对没有真正分开 | 守门=x3 时互遮 24→18,没清零 | 这类组对按多数方位定关系后,净隙必须 ≥ 组间距(允许推开),不能沿用原交叠量 |
| c | 线遮修补循环太弱 | 旗舰件线遮 +2–9 | 修补循环加轮数与多方向试探;目标是线遮零新增 |
| d | 20 件约束成环(全部 K2 家族、3 件社区件、1 件测试件) | 全梯子不可解,只能保底 | 刚性约束与「必须分开」冲突时,按最小位移放开必要的刚性对 |
| e | 解叠会显著撑大「作者堆放节点」的件 | Qwen21-Turbo-9步-全功能 面积 +79% | 堆叠节点默认不动、只报告;是否解叠由用户定(假设清单 A11) |
| f | 档位梯子是整件统一档 | 一个作用域过不了守门就整件放松 | 按作用域各自选档 |

## 七、结论

1. 保序压缩**方法成立**:只收不推、次序全保、左向与 est 间距零新增、恒等档逐坐标恒等。
2. 它解决的是**空隙过大**:22 件效果明显(含道劫主力件),其余 99 件空隙本来就不大。
3. 它**不能**让长流水线变短。整治后整图缩放 <0.5 的件数基本不变(93→92)。「一屏看清全貌」对大件需要重排(折行),那是另一种风险等级的工作,须用户单独决定。
4. 组框互遮与出组框是确定性的几何问题,可以清零,但要与节点位置联立求解,并允许最小必要的推开;原型的这一部分需要重做。
5. 守门与压缩真实冲突:旗舰件最紧档要付 0–7 对交叉的代价。线遮可以靠修补做到零新增;交叉增量是压缩的固有代价,须用户给容差。
