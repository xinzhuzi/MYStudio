# 视频质检人物问题：实现与证据边界

更新：2026-11-07（补「人审金标回写与召回门」一节）。此前 11-05 关于“Phase 1 已完成”、几何阈值已标定、VBench 检测器未开源及 VAD 能验证口型同步的表述不成立，当时已更正。

## 实际检测链

- `apps/backend/face_qc/worker.py` 使用 YuNet 检出人脸，记录尺寸、可判读比例和未标定的表观距离。YuNet 有五个关键点，但这些特征不是解剖异常分类器。
- `apps/frontend/lib/studio/qc/vision-preflight-runner.ts` 调用绑定的图片理解模型：单帧检查可见脸、手、肢体、画面文字及装配问题，相邻镜中帧成对检查身份和画风差异。
- `apps/frontend/electron/rendering/plugins/videoqc/chapter-qc-verdicts.ts` 按码归类判定：具体异常优先 `fail`，证据不全为 `unverified`，都不能放行。应用入口是 `ChapterQcReportCard`，结果经 `chapter-qc-ipc.ts` 回写并重算需求板；这条「真 runner 产物 → 回写 → 重算」链路由 `chapter-qc-ipc.test.ts` 钉住：缺证时已检出的人脸异常仍存活，其余维度不冒充通过。

## 本轮修复

1. 移除无标定依据的几何判病字段，修复 worker 读取不存在的 `width/height` 导致有脸反而报错；描述子裁剪与可辨尺寸均限于画面内区域。
2. 模型可返回 `pass: null`，必须写缺证原因；已经发现的异常仍保留。看不清不能回答通过。
3. 硬切或边界三帧不齐时不漏掉已提取帧；逐次隔离读帧失败，不丢此前发现。
4. 单帧不接受口型同步或跨镜身份码，成对调用只接受跨镜码；混合回复保留适用异常，不用重试把异常洗成通过。
5. 验收核查调用覆盖、逐镜中帧、抽帧错误和回写计数；具体异常优先失败并带镜号，不能因存在 preflight 对象就放行。
6. 未排除出镜说话的镜头仍缺口型同步证据。静帧及 VAD 不能替代音画时序判断；普通“已看完/已听完”勾选不自动覆盖此缺口。
7. 缺中帧的缺证原因写明是哪一镜（极短镜抽不出探针帧时用户能自己去定位），并要求 `visionSamplePoints` + `buildVisionDecisions` 的实际调用数等于验收算式 `帧数 + 决策数 - 1`——`chapter-qc-vision.test.ts` 把这条跨层算术钉在一起，改抽帧点不改算式会立刻红。

## 能力限制

YuNet 可辨尺寸达标不等于人物正常；表观距离未标定，不能当身份或畸形阈值。单帧模型只检查探针帧可见内容，不能证明全片逐帧无异常，也不能判断口型同步。VAD 只定位语音活动，不判断台词内容或对口型。

单测证明执行和三态契约，不证明模型召回率。旧争议手部裁片没有可信人审金标；人为注入额外嘴部的对照只能验证明显缺陷能否穿过检测链，不能代表自然生成异常的检出率。

## 实测入口

`apps/build/scripts/qc-vision-live-probe.ts` 用现有本机 LM Studio 调用实际 runner 和需求判定，保存模型原文、统计、发现及 verdict，不改应用报告或用户设置。素材、来源清单和结果在 `apps/output/qc-people-1105/`，运行态证据不作为人审金标；`live-report.json` 是 8 案首轮，`final-controls-report.json` 是修复后代码对「注入额外嘴部」和「极低清」两案的复跑，`verification-summary.json` 汇总当轮测试、侧车出数与范围外门禁失败。

尚需覆盖真人、动漫、小脸、遮挡和多人物的人审正负样本，才能标定召回与误报；目前不承诺检出所有人物问题。

同层另一件探针 `apps/build/scripts/qc-face-crop-live-probe.ts`（1107）只走生产函数与生产 ffmpeg 口径出图，不调多模态模型、不回写 App：同一批时间点同时产「限宽 1280 整帧」和「原始分辨率头部裁片」两套 jpg，再喂 `qc_face_detect_probe_1102.py` 量同一张脸在两种输入字节里各占多少面积。素材与读数在 `apps/output/qc-people-1107-absorb/crop-probe/`（运行态，不入 git）。

## 人审金标回写与召回门（2026-11-07）

上节那句「尚需人审正负样本」此前没有写入路径，样本无从攒起，召回也就无从计算。本轮补上这条闭环的两端：

- 写入口：体检单每行末尾的「有问题／没问题」两个按钮，走 `chapterQc.submitCalibrationCase` → 主进程 `chapter-qc-submit-calibration-case`（`apps/frontend/electron/ipc/studio/chapter-qc-ipc.ts`）。渲染端只交 `requirementId` 和 `label`；机器那半边 `verdict` 由主进程从落盘报告当行快照，报告 `createdAt` 用 `expectedCreatedAt` 乐观锁核对，陈旧报告直接拒收。
- 记的是什么：`label`（人答「这行的问题在这片子里到底有没有」）+ 打标当时这行的 `verdict` + 由成片 `outputSha256` 派生的 `caseId`。同片同行再点即覆盖（`upsertCalibrationCase`），不是历史堆。库落 `<remotionWorkspace>/qc/calibration/<seriesId>.json` 的 `cases`，半截条目（无 `verdict`／无 `at`）按「本仓不认」过滤，不计入 `caseCount`。
- 读的地方：`scoreCalibrationSet` 在编排器和回写口都算出逐行 `caseScores`（进报告、进板的行 tooltip），`caseRecallBlocker`（`chapter-qc-calibration.ts`）在 `buildChapterQcRequirements` 里判定——负例攒满 `QC_CALIBRATION_MIN_RED_CASES`（3）条而这门一条没抓回，判为摆设，把 `pass` 压成 `unverified`；抓回过一条、或负例不足 3 条，只在 `note` 里记账；已在报警的 `fail` 永不改判，标定账不许藏病。
- 计数口径：召回吃的是库里各条打标当时的 `verdict`，不是本轮这章的判定——本轮还没有金标可言，拿它算召回等于自己给自己打分。

边界：金标量为 0 时召回门不动作，没有金标的报告与上一版逐字相同；这套门证明的是「这门有没有抓得住的能力」，不证明覆盖率，逐帧与自然异常分布的限制仍见上节。

## 人脸原始分辨率裁片喂预审（2026-11-07，吸收件②）

「能力限制」一节记过：同一章出片，1080P 的脸中位短边 71px、608×352 只剩 22px；而 L5 探针帧整帧限宽 1280，1080P 拷到预审输入里脸只剩 ~47px——模型对这种尺寸的标准答复是「看不清就不判」。1107 又否掉了一条捷径：720×1296 真人件上把 YuNet 检测输入换 512／768／960 三档，检出数恒 16，放大检测输入不补召回。剩下的唯一杠杆是**让脸占满输入视野**：不缩整帧，而是把这一镜里脸实际占的那几十像素按原始分辨率整份交出去。裁片不新增细节，它只停止把细节浪费在无关像素上。

- 供给侧（`apps/backend/face_qc/worker.py` 的 `crop_faces`，`--at 0.633,1.898 --crop-out <dir>`）：检测仍在 512 方框空间跑，回到原生分辨率再裁——1280×700 这类非方帧上 x／y 缩放系数不同，检测框在原生帧里会变长方形，这条算错就把脸裁歪。方形边长取 `max(w,h) × 1.5`（留五官以外的上下文），夹回画面内不出负坐标；短边不足 `CROP_MIN_SIDE=256` 才 Lanczos 放大；JPEG q95 落成 `face-crop-{序号}-t{时间}.jpg`，就落在既有 `vision-frames/` 目录里——渲染端 `readFrameDataUrl` 一字不改就能读到。
- 台账（吸收件①的同一条纪律：缺证必须点名到镜）：每个请求时间点**恰一条**，状态四选一 `crop／no-face／read-failed／write-failed`。`no-face` 是合理的空证据（1102 已亲检背面镜、靴子特写确无人脸），不算缺口；后两种是真缺证，逐镜记 `index` 与 `tS`。TS 侧 `runChapterQcFaceCrops`（`chapter-qc-face.ts`）拿 `len(crops) == len(timestamps)` 当硬门，条数对不上整批判为不可用——宁可整批缺证，也不拿半截台账当证据。`--at` 给了但没给 `--crop-out` 直接 `crop-out-required` 拒收，时间串里有一条读不成有限数就整串拒收。
- 消费侧（`chapter-qc-vision.ts` 的 `registerFaceCropFrames`）：只给每个 `mid` 探针帧挂它自己那一张裁片，帧 `kind` 新为 `"face"`。覆盖等式 `expectedCalls = frames + decisions − 1`（`chapter-qc-verdicts.ts`）不动——一张裁片恰好吃掉一次调用，不新增计数器，所以看板不会把「查得不够」误判成缺证。裁片的预审提示词（`vision-preflight-runner.ts` 的 `buildFaceCropPrompt`）只问五官与脖颈，并显式写死「本图里没有手、全身、字幕和画面文字，不要对这些部位下任何结论」，问题码白名单收到 `FACE_CROP_ISSUE_CODES = ["face-anomaly"]`；侧脸与二维风格化不算缺陷，「看不清」不许答成「没问题」。
- 门禁：`chapter-qc.face.crop`（info，报 `produced/noFace/gaps/requested`）与 `chapter-qc.face.crop-gap`（warn，点名第几镜）。缺口只压人物这两行——`face-readability` 与 `character-integrity` 从 `pass` 降 `unverified`；已经在报警的 `fail` 一律不改判，裁片失败不能替人物问题洗白。`vision-reviewed／text-integrity／cross-shot-coherence` 明确不受裁片缺口牵连：那三行的证据来自整帧探针与成对任务，裁片没出成不构成它们的缺证。
- 实测（本机真片，`npx vite-node --config build/timeline/vite-node.config.ts build/scripts/qc-face-crop-live-probe.ts <mp4>...`，与生产同一函数、同一 ffmpeg 口径）：同一张 YuNet（512 输入）量「脸在送进预审模型的字节里占多大面积」——1080P 章节件远景脸整帧只占 **0.11%–0.12%**（6 个采样点里还只有 2 个检得出来），裁片后占 **81.1%**（原生 43.2px 的脸 Lanczos 进 256 方框）；真人特写件整帧 3.1%–3.8%，裁片 31.8%–40.8%（原生 242–258px，无需放大）。无脸对照件 6/6 记 `no-face` 且 `gaps=0`——空证据不等于失败，这条分开记账才让「这章没脸」和「裁片没出成」在报告上是两句话。越界时间戳逐条记 `read-failed` 而不是静默丢弃。回归：`apps/backend/tests/test_face_qc_worker.py` 16 项（裁片契约 8 项，托管 Python 带真 cv2 全绿）；前端 `chapter-qc-face／vision／verdicts／orchestrator` 与 `vision-preflight-runner` 五件 114 项，含一条走生产链的裁片侧车实跑（无脸 3 镜 ⇒ 台账 3 条 `no-face`、不产生 `face` 帧、不出 `crop-gap`、报告落盘台账与内存逐字相等）。
- 边界：没配托管 Python 的机器上本轮根本不尝试裁片，那只写一条 note——`face-readability` 本来就因「侧车未出数」压着 `unverified`，`releasable` 依旧过不去，不需要第二道门来兜。裁片喂的是五官维的分辨率，人物问题的召回率仍要等上节的金标负例攒够才有数字，本仓不承诺检出所有人物问题。
